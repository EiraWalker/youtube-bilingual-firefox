# 分段翻译与提前缓冲：需求对齐草案

日期：2026-10-10。状态：核心行为已对齐，PRD 与任务拆分已起草，尚未实施。当前需求以 [PRD](prd-buffered-subtitle-translation.md) 为准。

## 已明确的方向

- 用户要求改用分段翻译，让双语字幕逐步可用，类似流媒体提前加载。
- 每次请求需要包含有一定规模的字幕，避免小请求频繁往返、后续译文追不上播放。
- 新方向取代此前“通常一个轨道只发一次翻译请求”的约束。
- 沿用 Firefox、YouTube 播放器内双语字幕、OpenAI 兼容 API，以及完整源轨道获取。
- 沿用已确认的后台继续完成、保存译文及原文/译文/双语 SRT 导出需求。

## 当前实现与差距

0.2.3 的后台按整个视频任务串行翻译，只有全轨成功才公开译文并允许双语显示。长度错误触发的二分也不公开中间结果。播放位置不会影响队列次序，因此新增分段请求本身还不足以形成可播放的译文缓冲。

## 方案方向

- 首段优先覆盖当前播放位置，让首批双语字幕尽早可见。
- 后续段更大，提前翻译将要播放的内容；一段校验成功即可用于显示。
- 以“播放位置之后连续可用的译文时长”衡量缓冲，考虑倍速和字幕空白区。
- 根据实测请求耗时与字幕密度调整段大小和预取提前量，同时设定单请求文本上限。
- 保存已完成片段，整轨完成后仍可导出完整 SRT；本次不增加部分译文 SRT。
- 首段和常规段的具体时间/文本上限需要结合用户可接受的等待时间及真实 API 测量决定，不承诺未经验证的延迟。

## 第一轮已确认

1. 字幕尚未就绪或缓冲耗尽时，继续播放视频与原字幕。
2. 首批译文以等待不超过 20 秒为优化目标。该数值指首批等待时间，不是每段覆盖的视频时长；实际接口延迟仍需测量。
3. 每个视频同时进行的翻译请求上限为 3，跨视频规则由第二轮明确。
4. 用户对跳转问题答复为“等待远程回传”；第二轮进一步确认已发送请求等待返回，空出的名额优先处理跳转位置。

## 第二轮已确认

- 跳转后，已发送请求继续等待返回并保存结果；空出的名额优先处理新播放位置及其后续片段。
- 用户选择每个视频独立拥有 3 个并发名额。切换到新视频后，新视频可另开 3 个请求，旧视频的请求和后台翻译继续运行；不采用全扩展共用 3 个名额的建议。例如两个视频同时翻译时最多 6 个请求。
- 当时要求翻译失败时在页面右上角弹出错误信息；此项已被下方最新指令取代，不再作为实现要求。

## 最新确认：自动重试与控制台错误

用户明确要求：「报错后自动重试，仅控制台报错以便于测试」。因此采用自动重试，测试阶段不弹页面错误提示。保留已完成片段，其他可继续的片段继续翻译；正常进度可以显示等待重试，错误详情仅进入脱敏后的控制台日志。

建议默认对临时网络或服务错误最多额外自动重试 2 次，采用退避；用尽后允许手动恢复未完成部分。无效密钥等配置问题暂停，不无限重复请求。重试次数、退避和错误分类属于工程建议值，未单独获得用户确认，详见 PRD。

完整译文 SRT 沿用整轨完成后导出的行为，原文 SRT 在完整源字幕已获取后可导出。具体分段大小和预取提前量以 20 秒首批目标和每个视频 3 个并发名额为约束进行实测选择。任务拆分见 [issue 草稿](issues/buffered-subtitle-translation.md)，调度方向见 [ADR 0003](decisions/0003-buffered-subtitle-translation.md)。
