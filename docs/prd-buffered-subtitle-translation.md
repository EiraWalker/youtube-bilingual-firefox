# PRD：YouTube 字幕分段翻译与提前缓冲

日期：2026-10-10。适用产品：Firefox YouTube 双语字幕扩展。基线版本：0.2.3。

状态：需求整理完成，工程默认值与 issue 拆分待评审；尚未实施。本 PRD 取代此前「通常整轨只发一次翻译请求」的限制。错误处理以最新指令「报错后自动重试，仅控制台报错以便于测试」为准，取代右上角弹窗方案。

## 1. 问题与目标

当前版本以整轨为任务排队，只有整轨翻译成功才向播放器提供译文。即使因长度限制拆分请求，也不会逐段显示。较长视频因此需要等待全部翻译，播放位置变化也不能影响翻译顺序。

本次优化保留完整源轨道获取，将翻译改为分段提交、完成即保存和显示、提前翻译后续内容。首批采用较小片段以降低等待，后续采用较大片段以摊薄网络和模型调用成本。整轨最终仍会完成，支持再次观看与完整 SRT 导出。

成功表现：用户开启翻译后能较快看到当前位置的双语字幕；后台持续补充后续译文；跳转、切换视频、某个请求失败都不会丢失已有译文。

## 2. 已确认需求

| 编号 | 要求 | 验收含义 |
| --- | --- | --- |
| R1 | 一个选定语言轨道，完整获取源字幕 | 不改成依赖当前屏幕文字，也不同时翻译全部语言 |
| R2 | 分段翻译，避免过于琐碎 | 一次请求处理多条连续字幕；正常路径不逐条请求 |
| R3 | 字幕未就绪时继续播放 | 当前条目无译文则显示原文，不自动暂停视频 |
| R4 | 首批等待以 20 秒为目标 | 指首批可用译文的等待时间，不是片段覆盖时长；真实 API 延迟需测量 |
| R5 | 每个视频独立 3 个并发请求 | A、B 两个视频可同时有 6 个请求；旧视频继续完成 |
| R6 | 跳转不取消已发送请求 | 等待远程结果并保存，空闲名额优先补齐新位置 |
| R7 | 自动重试，测试阶段仅控制台报错 | 无页面错误弹窗、系统通知或 alert |
| R8 | 后台继续、保存译文、支持 SRT | 导出保留原文、译文、双语三种选择 |

继续沿用 Firefox、YouTube 播放器内显示、OpenAI 兼容 API、已有设置界面与字幕获取逻辑。API 地址、密钥、模型来自现有设置；本文件不包含凭据。

## 3. 用户故事

- **US1**：我开始观看时，希望先取得当前位置附近的译文，不必等待整段视频。
- **US2**：我持续观看或使用倍速时，希望后台提前准备足够译文，同时避免大量小请求。
- **US3**：我跳转后，希望下一批优先翻译新位置，之前已发送的请求仍能保存结果。
- **US4**：我切换视频或关闭旧标签页后，希望旧任务继续，新视频有自己的 3 个并发名额。
- **US5**：服务临时失败时，希望自动重试，已完成的片段保留，其他片段仍能推进。
- **US6**：测试失败场景时，我希望从控制台看到可定位的信息，页面不反复弹窗。
- **US7**：我希望再次观看时复用已保存片段，整轨完成后导出完整字幕文件。
- **US8**：我升级后，希望已有完整译文、设置和导出能力保持可用。

## 4. 播放与显示

1. 开启翻译后先复用匹配缓存；缺少完整源字幕时沿用整轨获取流程。
2. 以当前播放位置为首要翻译位置，不默认总从视频开头开始。随后补齐全轨未翻译内容。
3. 一个片段的译文通过完整性校验并成功保存后，立即提供给播放器，无需等待其他片段。
4. 显示以当前字幕条目是否有有效译文为准，不再用「整轨完成」作为双语显示条件。无译文时显示原字幕；已完成其他片段仍可正常显示。
5. 保留正常进度信息，如「正在翻译」「等待重试」和已完成条目数量。测试阶段页面不展示错误详情或错误通知；控制台承担错误诊断。
6. 不更改源字幕时间戳。片段乱序返回时按源条目标识合并，不能串行覆盖或显示到其他视频。

## 5. 分段与缓冲

### 5.1 分段原则

按连续字幕条目分段，边界不截断单条字幕。单请求同时受覆盖时长和文本量限制，达到任一限制即停止加入条目。已发送片段的成员固定；尚未发送的内容可根据跳转或缓冲情况重新分段，但不能重复覆盖已完成或在途条目。

以下是**工程建议初始值，并非用户确认的最终参数**，实施时需以测量结果调整：

| 参数 | 初始建议 | 调整依据 |
| --- | --- | --- |
| 启动批次 | 3 个较小连续片段，各最多约 60 秒源时间或 1,200 个源字符 | 首批可用时间、字幕密度、服务耗时 |
| 常规片段 | 最多约 180 秒源时间或 6,000 个源字符 | 翻译吞吐量、缓冲余量、输出限制 |
| 缓冲充足后的片段 | 可扩大至约 300 秒，仍受文本上限限制 | 减少请求次数，不牺牲当前位置补齐 |

单条字幕超过文本上限时允许作为单独片段提交；服务明确拒绝长度且无法进一步拆分时，记录可定位的失败，不无限递归。需要上下文时只提供有限相邻条目作为只读参考，要求返回的仍是本段目标条目，不在每次请求重复发送全轨。

每段请求取得完整、可校验的翻译结果后发布；本次不要求使用 API 的 token 流式输出。

### 5.2 缓冲定义与调度

「译文缓冲」指从当前播放位置向后连续可用的字幕时间范围。遇到第一条未翻译字幕即截断，不能把隔着缺口的远处译文计入连续缓冲。完整源时间轴中已知没有字幕的空白区不视为缺译。按播放倍速换算可支撑的实际观看秒数。

调度优先级依次为：当前位置缺口、紧接当前位置的缓冲、全轨剩余内容。参考近期请求耗时与播放倍速决定提前量；建议先以请求耗时的约 2 倍作为安全余量，再依据实测调整。缓冲充足时采用较大段继续完成全轨，不停止后台任务。

单片段重试等待期间不占用在途请求名额；真正重发时必须重新取得名额。

## 6. 并发、跳转与后台行为

- 并发上限按**视频**计算，每视频最多 3 个实际在途翻译请求。同一视频的不同任务或轨道不能各自再占 3 个；不同视频分别拥有名额。
- 同一视频、源轨道、目标语言及翻译配置相同的多个页面复用任务，避免重复收费。不同配置的结果隔离。
- 跳转立即更新待翻译优先级；已发送请求继续等待、校验与保存。三个名额都忙时等待第一个名额释放，不额外开第 4 个请求。
- 不为已经在途的目标范围发送重复请求。旧位置结果返回后不能覆盖新位置的显示状态。
- 多页面观看同一视频时，最近一次明确播放交互/跳转决定优先位置；后台页面的周期性上报不能持续抢走该优先级。各页面仍按自己的播放位置显示字幕。
- 切换视频、关闭标签页或关闭字幕显示不取消后台任务。A、B 同时运行可达到 6 个在途请求；旧视频继续补齐和保存。
- 用户明确取消任务时停止该任务的请求与自动重试；不影响其他视频。浏览器完全退出后无法继续执行。
- 更改轨道、目标语言或翻译设置时隔离任务身份；迟到结果只能写入原任务，不得污染新任务。

## 7. 自动重试与控制台诊断

用户已确认自动重试和仅控制台报错。以下错误分类、重试次数与等待时间属于**建议默认策略**：

| 情况 | 建议行为 |
| --- | --- |
| 网络中断、请求超时、HTTP 429、临时服务错误 | 每片段首次请求之外最多自动重试 2 次；建议等待约 2 秒、8 秒并增加小幅随机延迟；服务提供有效等待时间时优先遵守 |
| 返回格式错误、缺少条目、条目标识重复或不匹配 | 不发布该段无效结果，按同一有限重试预算重试 |
| 明确的输入/输出长度限制 | 只拆分失败片段并重试；设定有限拆分深度，以单条字幕为最终边界 |
| 无效密钥、无权限、错误配置或其他明确不可重试请求错误 | 暂停受影响任务，控制台说明原因；修改配置后允许恢复，不无限重复请求 |
| 本地保存失败 | 保留已取得的有效结果，重试保存；不能因为存储失败重复调用翻译 API |
| 用户明确取消 | 不自动重试 |

重试耗尽后，保留失败范围与已有成功片段，其他可处理片段继续；整个任务不能误标为完成。用户可对未完成部分发起恢复/重试，不重新翻译已成功片段。

错误仅记录到对应的扩展后台/页面控制台。日志至少包含视频标识、片段范围、尝试序号、错误类别、HTTP 状态（如有）、耗时和下一步动作。禁止记录密钥、Authorization、带敏感参数的完整地址、完整字幕正文或原始响应体；第三方错误消息也必须经过脱敏。可在现有帮助说明中注明 Firefox 扩展后台控制台入口。

## 8. 保存、恢复与导出

- 每个完成片段独立保存，之后的失败、跳转、切换视频不能丢失它。
- 缓存身份至少区分视频、源轨道语言与人工/自动来源、源内容指纹、目标语言、服务与模型及会改变翻译结果的配置；不得把明文密钥写入任务元数据或日志。
- 保持 0.2.3 完整缓存兼容；可读的既有完整任务不应因升级而重新收费翻译。
- 建议浏览器重启后先恢复已保存状态；用户再次开启或点击恢复时只翻译缺失部分，不在浏览器启动时静默发起付费请求。
- 原文 SRT 在完整源时间轴取得后可导出。译文和双语 SRT 仅在全部源条目都有有效译文后允许导出；部分完成时显示进度和未完成状态。
- SRT 保持源条目顺序、时间戳及数量；双语 SRT 的每条包含对应原文与译文。缓存不匹配时不能混合导出。

## 9. 指标与验收

### 9.1 时间与连续性

首批等待起点为有效设置下用户开启翻译的时刻；终点为**返回时当前播放需求附近**的首段有效译文可供播放器使用。单独记录源字幕获取、排队、远程请求、校验保存各阶段耗时。已经播放过去的首段返回不算当前位置首批成功。

20 秒是需要用实际服务验证的优化目标，不作为远程服务无条件保证。无字幕空白区要分别记录「范围已可用」与「第一条实际显示」，避免人为放大等待。冷启动与缓存命中分别统计。

持续播放统计可用译文覆盖率、缺译持续时间、每分钟视频对应的请求数、实际并发峰值及调用失败/重试次数。若远程翻译吞吐低于播放消耗，应如实显示原文并记录指标。

### 9.2 必测场景

| 场景 | 通过标准 |
| --- | --- |
| 一段先返回、其他段尚未完成 | 先返回段保存并可显示；未完成区域原文可见，视频未被暂停 |
| 乱序响应、密集字幕与稀疏字幕 | 条目无丢失/重复/串位；缓冲不跨未翻译字幕缺口 |
| 1 倍及 2 倍速、响应耗时变化 | 提前量响应实际消耗，后续请求保持多条字幕规模 |
| 三请求在途时跳转 | 原请求继续；下一空闲名额处理新位置；同视频不超过 3 |
| 两视频并行，关闭旧标签页 | 新旧视频可各 3 个在途；旧任务继续保存且不向新页面串字幕 |
| 同视频多页面与重复开启 | 匹配任务复用，无重复翻译请求 |
| 临时失败后成功、失败耗尽、取消 | 有限自动重试；保存部分保留；取消不重试；页面无错误弹窗 |
| 存储失败、浏览器重启、升级缓存 | 不重复支付已成功片段；恢复时只补齐缺失部分；旧完整缓存可读 |
| 三种 SRT 导出 | 完整性门槛、条目数、顺序、时间戳、双语配对正确 |

用可控延迟和失败的模拟服务先验证行为与并发不变量，再使用实际服务验证端到端首批速度。真实回归视频包含 `6AgOfiZOWiY`、`uwS__WiOYTI`；每个视频建议至少 3 次冷启动记录，并补充缓存命中记录。真实字幕不可取得或服务不可用时明确标记环境阻塞，不把模拟测试当作真实视频通过。本次仅撰写文档，不发起这些翻译请求。

## 10. 实施边界与交付

首先在首段显示切片中完成必要的兼容性重构：解耦整轨完成状态与条目可显示状态，让片段保存、任务公开状态和渲染流程支持增量结果。随后增加并发缓冲、跳转调度、多视频后台、重试和恢复导出。每个切片均有可演示的端到端结果，避免按前端/后台/测试横向拆票。

不包含其他站点、语音转写、全部语言同时翻译、直播支持、部分译文 SRT、自动暂停视频、全扩展共用三个名额或新的配置页面视觉改版。

完整 issue 草稿见 [任务拆分](issues/buffered-subtitle-translation.md)。现有需求演进见 [对齐记录](buffered-translation-alignment.md)。尚待评审的参数不影响用户已确认的核心行为；实施时若测量要求改变这些行为，应重新对齐。
